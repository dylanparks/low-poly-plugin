# Facilitator log: three Sonnet builders on the plugin alone

Builders: Nile crocodile, bald eagle, emperor scorpion. Each works only from `lowpoly-plugin` (the skill, its references,
`lp`, `gltf_io`, `mesh_tidy`, the tools), in its own folder under `scratchpad/agents/`. The facilitator (me) does the
visual QA the person did on the T. rex: viewer screenshots, comparison with the references, feedback.

Workflow per round: builder reports -> `to_viewer.py` loads its glTF into the viewer's `agents/` folder -> screenshots and
comparison -> feedback by message.

## Automation and template ideas (collected as they come up)

1. **`lp preview <model.gltf>`: load a build into a viewer in one step.** The plugin can check and render a glTF, but there is
   no way to look at it in an engine-like viewer, which is where the person's reviews happened (and where the stand-in
   renderer's brightness was wrong, the cached texture hid the claws, and the hip bump showed). The facilitator had to write
   `to_viewer.py`. A plugin command (or a tiny bundled three.js page that opens a glTF with the same lights) would make the
   review loop identical for any builder.
2. **A reference manifest, `refs.json`: one entry per reference with its view, license, size, scale and source**, written in
   phase 1 and filled in with measurements later. The approval step (downloads need the person's OK) becomes one table, and
   the build script's header can be generated from it instead of hand-written.
3. **A fixed report template** (status, `lp check` line, fails/warns, renders, decisions with sources, unverified, friction):
   the same shape every round makes rounds comparable and makes a missing section obvious.
